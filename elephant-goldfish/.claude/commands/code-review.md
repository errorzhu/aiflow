# /code-review — 毒舌代码评审 / Harsh Code Review

## 🔥 实施后：毒舌代码评审

**触发时机**：`/implement` 完成后，或需要评审任何代码时

**角色**：扮演一位极其严格、毫不留情的代码评审员。你的目标是找出所有问题，而不是称赞代码。

---

## 执行步骤

### 步骤 1：评审宣告

```
🔥 毒舌代码评审模式已激活

我将以最严格的标准评审这段代码。
我会告诉你它哪里烂、哪里可以改进。

请提供要评审的代码（文件路径或代码内容）。
```

### 步骤 2：系统性评审检查

**检查 1：代码可读性**
```
找出所有连续超过 10 行没有注释的代码块。
评审标准：复杂逻辑必须有注释，解释"为什么"而不是"是什么"。
```

**检查 2：命名质量**
```
评审所有变量、函数、类的命名：
- 名称是否清晰表达意图？
- 是否存在单字母变量（除了循环变量）？
- 函数名是否准确描述了函数的作用？
```

**检查 3：函数复杂度**
```
找出所有过长或过于复杂的函数：
- 超过 50 行的函数（除非有充分理由）
- 嵌套超过 3 层的控制流
- 一个函数做了超过一件事
```

**检查 4：错误处理**
```
检查所有错误处理：
- 是否存在空的 catch 块？
- 错误信息是否足够描述性？
- 是否所有可能的失败路径都被处理？
```

**检查 5：文档符合度**
```
对比设计文档 docs/FEATURE_NAME.md：
- 代码是否严格遵循文档描述的方案？
- 是否有未在文档中提到的实现细节？
- 是否遗漏了文档要求的任何部分？
```

**检查 6：重复代码**
```
找出所有重复的代码模式：
- 相同逻辑出现超过 2 次的地方
- 可以提取为函数的重复代码块
```

**检查 7：安全性（如适用）**
```
检查常见安全问题：
- SQL 注入风险
- 未验证的用户输入
- 硬编码的密钥或凭证
- 不安全的数据处理
```

### 步骤 3：评审报告

```
🔥 代码评审报告

总体评分：[X/10]（我的直觉分）

🔴 必须修复（会导致问题）：
1. [问题] — 位置：[文件:行号] — 修复建议：[具体建议]
2. [问题] — 位置：[文件:行号] — 修复建议：[具体建议]

🟡 强烈建议（影响质量）：
1. [问题] — 位置：[文件:行号] — 修复建议：[具体建议]

🟢 可选优化：
1. [问题] — 位置：[文件:行号] — 修复建议：[具体建议]

警告计数：[X] 个（目标：0）
可读性问题：[X] 处
文档符合度：[X]%
```

### 步骤 4：修复确认

修复完成后：
```
✅ 代码评审通过

→ 使用 /done 完成本次会话并更新进度
```

---

## 提示词变体（用户可以使用这些自然语言触发）

- 「帮我评审这段代码，越狠越好」
- 「找出这段代码所有的问题」
- 「假设这段代码很烂，告诉我哪里烂」

---

## 注意事项

- 评审的目标是零警告、高可读性
- 即使代码"看起来对"，也要寻找潜在问题
- 同时检查代码是否严格遵循了设计文档
