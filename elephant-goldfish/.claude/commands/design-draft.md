# /design-draft — 生成设计文档草稿 / Generate Design Document Draft

## 📄 阶段 2：文档生成

**触发时机**：完成 `/design-start` 讨论后，准备将设计决策固化为文档

**前置条件**：必须已完成 `/design-start`，不能跳过设计讨论直接生成文档

---

## 执行步骤（逐段进行，不要一次性生成全文）

### 第 0 节：业务问题描述

提示词模板：
```
我现在开始为这个功能编写设计文档。

第 0 节（业务问题）：请用通俗语言描述我们要为用户解决的业务问题。
不要使用技术术语。写完后等我确认。
```

等待用户确认后继续。

### 第 1 节：技术实施计划

提示词模板：
```
第 1 节（技术方案）：用通俗语言描述技术实施计划。
- 核心组件有哪些？
- 它们如何协作？
- 该功能在系统生态中处于什么位置？
尽量少用专业术语。写完后等我确认。
```

### 第 2 节：已考虑的替代方案

提示词模板：
```
第 2 节（替代方案）：描述我们在讨论中考虑过但排除的方案，
以及排除的原因。同样使用通俗语言。
```

### 第 3 节：详细实施计划（最重要！）

提示词模板：
```
第 3 节（详细实施）：编写极其详细的实施计划。
你必须列举代码库中每一个需要修改或创建的文件，以及为什么需要这些更改。
格式如下：

**需要修改的文件：**
- `path/to/file.py`：原因说明
- `path/to/another.js`：原因说明

**需要创建的新文件：**
- `path/to/new_file.py`：用途说明

此阶段不需要写具体代码，但需要列出所有涉及的文件。
```

### 第 4 节：测试与验证标准

```
第 4 节（验证标准）：描述如何验证这个功能已正确实现。
- 功能测试：[具体场景]
- 边界情况：[列出]
- 成功标准：[可量化的指标]
```

## 文档模板

生成的文档应保存为 `docs/FEATURE_NAME.md`，结构如下：

```markdown
# 功能名称 设计文档

**状态**：草稿 / 已审阅 / 已批准  
**创建日期**：YYYY-MM-DD  
**最后更新**：YYYY-MM-DD  
**功能 ID**：F00X  

---

## 第 0 节：业务问题

[通俗描述]

## 第 1 节：技术方案

[通俗描述，核心组件及协作方式]

## 第 2 节：替代方案

[排除的方案及原因]

## 第 3 节：详细实施计划

### 需要修改的文件
- `file_path`：原因

### 需要创建的文件
- `file_path`：用途

## 第 4 节：验证标准

[测试场景和成功标准]

---

## 决策记录

| 决策 | 原因 | 替代方案 |
|------|------|----------|
| ... | ... | ... |
```

---

## 注意事项

- 每节写完后必须等待用户确认，不要一次性生成所有内容
- 文档是"唯一真理来源"——代码必须严格遵循文档，不是相反
- 完成后使用 `/goldfish-test` 进行验证
