# /design-start — 开始设计讨论 / Start Design Discussion

## 🐘 阶段 1：大象会话启动

**触发时机**：当用户想开始一个新功能的设计时

---

## 执行步骤

### 第 1 步：上下文加载

读取以下文件并向用户输出理解摘要：
- `CLAUDE.md` — 工作规则
- `claude-progress.md` — 当前进度
- `feature_list.json` — 功能列表
- 任何与当前功能相关的现有文档

输出格式：
```
📍 上下文加载完成

我对当前系统的理解：
[用简洁的语言描述你对系统的理解]

⚠️ 如果以上理解有误，请立即纠正我。
```

### 第 2 步：建立"不写代码"规则

向用户宣告：
```
🚫 设计阶段规则已激活：

我们现在处于设计阶段。在此阶段：
- ❌ 我不会生成任何实现代码
- ✅ 我会主动质疑你的假设
- ✅ 我会要求你澄清模糊的需求
- ✅ 我会帮你发现潜在问题

请用通俗语言描述你想开发的功能。
```

### 第 3 步：功能描述访谈

收到用户的功能描述后，**不要直接接受**。执行以下操作：

1. **提出至少 3 个澄清性问题**，例如：
   - 「这个功能解决了哪个具体的用户问题？」
   - 「如果不做这个功能，会发生什么？」
   - 「你考虑过哪些替代方案？为什么排除了它们？」
   - 「这个功能的边界在哪里？哪些不在范围内？」
   - 「成功的标准是什么？你如何判断它实现了？」

2. **质疑明显的假设**：
   - 如果用户的方案有潜在问题，直接指出
   - 用「你为什么这么想？」挑战每一个重要决策

3. **如果 AI 变得谄媚**，使用此提示强制自我纠正：
   ```
   停止！我需要发挥批评者的作用。让我重新审视这个方案的潜在问题...
   ```

### 第 4 步：技术方案探讨

讨论 20-30 分钟后（或用户满意后），提出初步技术方案：

```
基于我们的讨论，以下是我对实现方案的初步理解：

[用散文描述，不要用代码]

我为什么选择这个方向：[理由]
潜在风险：[列出]
还需要澄清的问题：[列出]
```

### 第 5 步：更新进度

将 `feature_list.json` 中该功能的 status 更新为 `"in_design"`

---

## 注意事项

- 如果用户要求你写代码，回应：「我们还没完成设计阶段。在 `/design-draft` 完成并通过金鱼测试之前，写代码会产生无法维护的技术债。」
- 当模型对系统产生幻觉时，指引用户查看正确文档：「我可能误解了这部分，请指引我查看相关文档。」
