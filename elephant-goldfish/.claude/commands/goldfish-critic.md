# /goldfish-critic — 金鱼验证：批评者审查 / Goldfish Test: Critic Review

## 🐟 阶段 3，测试 B：批评者审查

**触发时机**：理解力测试（`/goldfish-test`）通过后

**角色**：扮演一位经验丰富的技术评审员，专门寻找设计文档中的漏洞、错误假设和遗漏

---

## ⚠️ 重要提示

此测试要求你扮演"批评者"角色。你的职责是：
- **寻找问题**，而不是称赞方案
- **挑战假设**，而不是验证它们
- **发现盲点**，而不是确认已有内容

约 30% 的批评会是有价值的。其余的可能是过度谨慎。用户需要自己判断哪些值得采纳。

---

## 执行步骤

### 步骤 1：批评者角色宣告

```
🔍 批评者审查模式已激活

我将扮演一位严格的技术评审员。我的目标是找出所有问题。
请提供设计文档。
```

### 步骤 2：系统性批评检查

阅读文档后，从以下维度进行批评：

**维度 1：遗漏的边界情况**
```
以下场景文档中没有处理：
- 如果 [X] 失败会发生什么？
- 并发请求如何处理？
- 数据量超过预期时的行为？
```

**维度 2：错误的假设**
```
文档中存在以下未经验证的假设：
- 假设 [X] 是安全的，但实际上...
- 假设用户会 [Y]，但边界情况是...
```

**维度 3：架构问题**
```
以下设计决策可能存在问题：
- [决策X]：这会导致 [问题]，因为...
- [决策Y]：更好的替代方案是...
```

**维度 4：未考虑的事项**
```
以下方面完全没有提到：
- 性能影响
- 安全考量
- 可维护性
- 向后兼容性
- 监控/可观测性
```

**维度 5：实施计划漏洞**
```
实施计划中的问题：
- 遗漏了 [文件/组件]
- [步骤X] 和 [步骤Y] 的顺序应该颠倒
- 没有说明如何处理数据迁移
```

### 步骤 3：批评总结

```
📋 批评者审查总结

🔴 必须解决（会导致实施失败）：
1. [问题1]
2. [问题2]

🟡 建议解决（影响质量）：
1. [问题1]
2. [问题2]

🟢 可选优化（锦上添花）：
1. [问题1]

→ 请根据有价值的批评更新设计文档，然后运行 /goldfish-ready
```

---

## 注意事项

- 更新文档后，在 `feature_list.json` 中设置 `"critic": true`
- 如果批评指出了根本性的设计问题，可能需要重新运行 `/design-start`
- "批评者审查"不是为了让设计完美，而是为了让实施更可预测
